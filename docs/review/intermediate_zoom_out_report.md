# Stage 8 · Intermediate Zoom Out Review

- 目标：`README.md` 全文
- 前置：Stage 5（1B/10M/3N）、Stage 6（1B/3M/12N）、Stage 7（7B/31M/14N）
- 本轮不重述已记录条目，只做收敛与补盲

## 结论

**Q1：仍是"20 条规则 + 13 条降级"的清单，不是系统。** 唯一的组织轴是"相对 legacy 的差值"——那是账本，不是架构。

缺失的组织思想可以压成两句：

> (1) **无内核、无事务** → 只有"读全图 → 改内存 → 写全图"，一切依赖求值、交互、事务的能力不存在；
> (2) **只有部分 DWG 对象被建模，且只可写实体自身属性** → 一切依赖派生对象一致性的操作，要么丢失，要么必须重建实体（→ 换句柄）。

有了这两条，§6.2 的 13 行是 2 段推论，§5 的 20 行是 3 个效果族（改属性 / 增删实体 / 只读检查）。没有这两条，13 行就是 13 个各自成立的缺陷。

## A. 组织原则

### A1 [Blocker] 组织轴选错
- §1 全表、§6.1–6.2、§10.5 三处同一轴线各写一遍
- 后果：读降级必须先理解已废弃的插件；降级之间没有亲缘关系（丢对象与表格显示旧值同权重）；新增能力无处安放。
- 建议骨架：产品定义与非目标 → 两条硬约束 → 配置契约（Filter/Action/效果族）→ 执行语义 → 能力矩阵（由约束推导）→ 证据附录。

### A2 [Major] 20 条规则没有效果族，只有类型名
- 4 条默认不改图（`DimTextAudit`、`AttributeAudit`、`BomSync` 只读，`GeometryCleanup` 默认预演），其余 16 条分属"改属性"与"增删实体"。三者在失败语义、幂等性、可否并行、回滚代价上完全不同。
- 没有效果族，就无法回答"这条会不会动几何""跑第二遍还会不会改""两条能不能同批"。

### A3 [Major] 没有"执行语义"这一章
- 顺序、幂等、冲突、失败传播、写出时机散在 §3/§6.2/§9/§10.3 的散文里，且互相矛盾（D2/D7/D8）。矛盾能存在，是因为没有一处声明"这些是同一份语义的五个面"。

## B. 根因收敛：26 Major + 7 Blocker → 4 个根因

### R1 [Blocker] 配置没有独立契约层——schema 就是 C# 属性 + 反射
归入 Z1、Z3、Z4、C1、C2、C3、C5、C6、Y2、Y4、S2、D6、D10。

`RuleAction` 是 128 个可空属性的扁平并集，schema 由反射生成，于是**五个消费者各读一份反射面**：文档（手抄）、界面（`FieldCatalog`）、校验（`RuleValidator`）、摘要（`RuleSummary`）、legacy 兼容（`JsonExtensionData`）。五份副本必然漂移——Z4（默认值写三遍）和 Y2（两个字段名）不是笔误，是同一个设计选择的必然结果。

**只修一个根因就修这个。** 一份显式 schema 同时消灭 13 条发现。

### R2 [Major] "能力"只活在 README 的表格里，代码里没有这个对象
归入 Z7、D9、Y1、Y12、C14、S9（状态列语义过载）。

`CapabilityProbe` 只有 `TextMaskRule` 一个消费者；"表格能不能写"在四处有四种说法，因为四张表都是手抄的。能力应当是**数据**（`capability → supported/degraded/unsupported + reason + consumer`），被规则、preflight、预览、界面共同查询。

这也解释了 Z7：探测之所以进了运行路径，正因为规则没法问"这个能力现在什么状态"，只能自己现场探一次。

### R3 [Major] 没有分层边界，职责按"当时谁方便"分配
归入 Z2、Z8、C7、C8、S7、Z14。

证据：`Core/Editing/` 3288 行全是界面支撑物（`FieldCatalog`/`RuleSummary`/`RuleValidator`/`ConfigSaver`/`NameValidator`），却住在"与宿主无关的核心库"里；`Engine/TextColumns.cs`（控制台等宽列对齐）也在 Core。

边界不存在 → "legacy 平移"只能靠复制（Z2）、"测试工具"只能塞进产品二进制（Z8）、"命令参考"只能切成两半（S7）。

### R4 [Major] 文档体裁错位：这是"移植实验报告"，被当作"产品设计"使用
归入 Z11、S1、S3、S6、D1、D4、D12、D18、Y19。

因为项目没有设计文档，README 被迫同时承担论证职责，于是**实验证据被当作设计理由**（"与插件一致"当理由、"AUDIT 0 错误"当成功判据）。实验报告的合法结构不产生"非目标""备选方案""成功判据"——不是作者漏写，是这个体裁里没有这些格子。所以 D1/D4/S1 不该用"补一节"来修，应把证据整体降级为附录，正文按 A1 的骨架重写。

## C. 三遍都没看的维度（新发现）

### M1 [Blocker] 配置是唯一输入，但它没有校验边界——错误模式全是静默的
- `ConfigLoader.cs:26-38`、`BatchConfig.cs`；文档 §4 L168 把"原样接住"写成优点
- `MissingMemberHandling.Ignore` + `[JsonExtensionData]` → 键名拼错不报错，还被**原样保存回去**；`Error` 回调一律 `Handled = true` → 类型写错静默取默认值；`Version` 字段从不被读取。
- 杀伤力：**同一个错字在不同规则上后果相反**。`EntityTypes` 拼错 → `HasCondition==false` → 7 条规则 fail-closed 中止（安全）；同样拼错在其余 13 条上 → 无过滤条件 → **整图被改**（fail-open）。
- §9 标题叫"安全设计"，通篇讲数据保全（不覆盖源图），一个字没讲**输入信任**。

### M2 [Blocker] "输入集合与输出集合不相交"没被当作不变量，重复运行会自我喂食
- `Program.cs:815-821`（`CollectFiles`）、`:871-872`（默认输出根）
- 默认 `--out = <输入目录>\output`；`--recursive` 用 `AllDirectories` **不排除** `output\` 与 `.jun-runs\`。第二次运行把 `图纸\output\*.dwg` 当输入 → 写出 `output\output\*.dwg`，第三次再套一层。
- §9 的五条护栏全部围绕"别覆盖源图"，没有一条围绕"别把自己的产物当原料"。

### M3 [Major] 规则之间没有冲突模型，也没有幂等声明
- `EntityLayerChange` 与 `LayerMap` 都写图层；`SetByLayer` 放在 `EntityLayerChange` 之后会抹掉前者设的显式颜色；`PurgeUnused` 与任何"自动建层"规则互为逆操作，顺序决定清得掉还是清不掉。
- `Rules[]` 的顺序因此是**未声明的语义**，用户只能靠试。

### M4 [Major] 可回滚 ≠ 可追溯
- manifest 记录的是文件级事实（`Existed`、备份路径），不记录变更级事实（哪条规则、哪个句柄、旧值→新值）。`--preview` 能产出变更级事实，但它是运行前的、opt-in 的。
- 三天后审图发现某张图某层错了，工具只能"整批回到运行前"，无法回答"错在哪条规则"——修复只能猜，然后重跑 500 张。
- 前几阶段讨论的都是"回滚该不该存在""manifest 何时写"，没有人问 manifest **该记什么**。

### M5 [Major] 配置的跨版本演进是单向静默的
- `Version` 从不被读；`schemaVersion` 只写不校验；未知字段靠 `JsonExtensionData` 保活。
- 组合出的语义：**旧二进制读新配置不会失败，会带着旧语义跑完**。对"默认取安全侧"的工具这是最坏的一种兼容策略。

### M6 [Nit] §9 "安全设计"名不副实
- 五条全是数据保全；没有输入信任（M1）、路径越界（`BomExportPath`/`--out` 可指向任意路径）、正则 ReDoS（`MatchMode=Regex` × 500 张图）、共享目录并发。建议改名"默认值策略"，另设一节真讲安全。

## D. 范围判断

### S1 [Blocker] 声明范围（改图）与实现范围（三个产品）不一致
仓库里同时有三个产品：① 批量变换器（16 条写图规则 + 引擎）；② 图纸质检套件（4 条只读规则，产出是报告）；③ 配置编辑器（3120 行主窗体 + `Editing/` 3288 行 + 两个对话框 + 截图自检）。

README 只声明了第 1 个，所以第 2、3 个的功能无处安放——这正是 A2 无法成立的原因（"只读检查"这个效果族没被识别，因为它属于一个没被承认的产品）。这也解释了为什么"非目标"写不出来：声明范围之外的功能，既不能列为目标，也不能列为非目标。

判断：不是"做多了"，是**没声明做多了**。建议主产品=变换器，质检并入"只读效果族"，编辑器降为附属工具并在 §1 一句话交代。

### S2 [Major] 报表排版住在与宿主无关的 Core 里（`Engine/TextColumns.cs`）
### S3 [Major] `BomSync` 破坏"一条规则 = 改一份 DWG"的模型
- 它产出 CSV、读外部基准、只读不改图，却塞进同一个 `Rules[]` 与同一个 `IRuleHandler` 契约（`void Execute(ctx, result)`，无产物概念）。靠副作用写文件，而契约注释明确写着"不得自行写盘"。**文档与契约在这一条上直接冲突**。

## 复核意见（Elephant）

R1/R2/R3 成立，且 R1 确实是 13 条发现的共同根因。M1/M2 是我漏掉的真问题，其中 M2 比 D2/D8 更基础（跨运行语义）。M3/M4 成立。S1 的判断我接受一半：确实有三个产品，但"质检规则"与"变换器"共用同一套遍历与过滤，拆成两个产品会重复实现——正确做法是承认效果族，不是拆仓库。
