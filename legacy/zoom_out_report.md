# Stage 5 — Initial Zoom Out 评审报告

* **目标文档**：`docs/designs/rule-editor-form.md`（全文 625 行）
* **评审者**：egm-zoom-out（应用 `zoom-out-standard.md`）
* **日期**：2026-10-29

## 发现

### 🔴 单用户场景撑不起这个形状

文档自己写明：规则只有作者一人写，同事只按 Run。为一个人的"记不住字段名"付出 4 阶段、26 项改动、
10 个新组件、1 个新测试工程。

文档从未评估最省的路径：**每类型一份完整示例 JSONC + README 字段表**。`config.json` 现有约 230 行注释
已经是这份文档的雏形。Alternative A 把"文档"偷换成"补全引擎"（理由写"补全列表也需要一份字段清单"），
于是"只补文档、不写代码"这条路从未进入比较。

**建议**：先做示例配置 + 字段表，再判断是否还需要表单。

### 🔴 核心承诺不可验证

`AppliesTo` 与 handler 实际读取是两份账，文档自认断言无法证明，替代品是"读源码文本 grep 字段名"的冒烟测试，
并承认抓不住"读了但语义不同"。G1（只显示该类型用得上的字段）整个建立在这份无法验证的声明上；
错了比 JSON 更危险，因为表单看起来权威。

Alternative F（每类型强类型 Options）能从根上消灭 `AppliesTo`、残留清理、`VisibleWhen`、反射，
文档以"改动面最大"否决，却没量化：所选方案同样要动全部 59 个属性 + 10 个组件 + 两份账。

### 🔴 用自己的保存路径制造问题再打补丁

`config.json` 是带注释的 JSONC，那 230 行注释就是作者真正的文档。`SaveRules` 整段重写必然删注释，
方案是写 `.bak` + 状态栏提示。等于每次保存后让唯一用户去 `.bak` 里人肉重合并。

**建议**：要么结构化写回保留注释，要么把说明迁出 JSON 到 `.md`。不要用备份文件代替修复。

### 🟡 扩展字段袋为设计自身存在

`Extra` 保护的场景只由"表单编辑 + 手写 JSON 并存"产生，而 Non-Goals 已声明不提供第二编辑通道。
代价是永久的：模型多一字段、`Config` 引入 `Newtonsoft.Json.Linq`、序列化断言、
"另有 N 个未识别字段"UI、CUJ 6。可删，用户零感知。

### 🟡 拾取（P3，item 24–26）YAGNI

为省一次键入，新增独立桥（明确"不复用 `UiRunBridge`"，于是两条桥永久并存）+ 新命令 + 条件编译 + 日志。
整段可删。

### 🟡 `Default` 是第三份真相

`Default` 是显示用字符串，必须与 handler 运行时默认值手工一致，看守成本是"每个 `bool?` 字段一条回归测试"。
为显示"默认：是"付永久测试税。只显示"不设置"即可。

### 🟡 自造两个字符串 DSL

`Values="ModelAndLayouts=模型+全部布局;..."` 与 `VisibleWhen="路径 != 字面量"`：无编译期检查、
需解析器与错误处理，而全项目只有一两处联动（`ForceByLayer` → `LinetypeName`）。硬编码那一处即可。

### 🟡 CUJ 5 与 Alternative G 自相矛盾

用"自研类型不改 UI"否决 Alternative C；Alternative G 的否决理由却写"自研规则写在同一仓库内，这个优势用不上"。
同一前提两处反向使用。且"11 类型 × 10 字段"被夸大——文档自己说一条规则实际只用 3~6 个字段。

### 🟡 海拔失控

625 行里约 230 行是 26 个文件的逐文件改动清单（类名、签名、枚举、伪代码）。这是工单，不是设计；
真正需要评审的切分决策（数据 vs 代码）只有一段。

### 🟢 两处内部冲突

* Q2 称最近匹配阈值未定，item 3 已写死"距离 ≤ 2"；
* `RuleValidator` 返回 `FieldIssue`，`ConfigLoader` 立刻降级成 `string`——要么全程结构化，要么别引入 typed 模型。
