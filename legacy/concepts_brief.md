# 规则编辑页：从 JSON 文本框改为 schema 驱动的表单

* **作者：** Jun
* **日期：** 2026-10-29
* **状态：** 定稿 v1.0（6 视角评审完成，两处待裁决项已定：值域走保存时校验，布局走模态抽屉）

## 背景

`Jun.AutoCAD.BatchTool` 是一个配置驱动的 AutoCAD / 中望CAD 批处理插件。一份 `config.json` 描述若干条规则，
每条规则由 `Filter`（选中什么）和 `Action`（改什么）组成，插件按数组顺序执行。

规则模型是**两个共享的封闭类**（`Config/Jun.AutoCAD.BatchConfig.cs`）：

- `RuleFilter`（16 个字段）与 `RuleAction`（43 个字段），11 种规则类型共用；
- 所有字段可空，一条规则实际只用到其中 3~6 个；
- 哪个类型用哪些字段，目前只存在于各 handler 的代码里和 `config.json` 的注释里。

「规则编辑」页签（`UI/Jun.AutoCAD.BatchToolForm.cs`）现在是三个竖向堆叠的卡片：
配置文件卡 → 规则列表卡 → 一个多行文本框，里面是当前选中规则的 JSON。用户改 JSON，
点「保存规则到配置」时由 `Core/Jun.AutoCAD.ConfigSaver.cs` 整段替换 `Rules` 数组文本。

## 要解决的问题

1. **不知道有哪些字段、每个字段能填什么值。** 想按文字内容筛选找不到入口；手敲 `AR-CONC`、
   `A1_TITLE`、图层名打错一个字符就 0 命中，且没有任何提示。
2. **改规则靠手写 JSON**，对非作者不友好。

使用场景（用户确认）：规则**只有作者一人编写**，写好后交给不写代码的绘图同事执行；
同事不改规则，只需看懂"这条规则在做什么"；作者会**在本仓库内**新增规则类型；11 种内置类型全部覆盖。

## 分析（6 视角评审的合并结论）

### 一、原设计的核心假设被推翻：schema 不能"属性标注 + 注册表"两处拼

三个视角独立指向同一处：把标签、控件种类、单位标在 `RuleFilter`/`RuleAction` 属性上，
再维护一张"规则类型 → 字段清单"的注册表，**不是单一来源，是两份账**。

- 标签写属性、分组写清单，同一字段被两个类型引用而分组不同时没有裁决规则；
- 更致命的是防漂移断言**恒真**：字段都躺在共享的类里，"路径能在模型上找到属性"必然成立，
  它检不出真正要防的漂移——"清单声明了 X，但 handler 根本不读 X"。
- 而"handler 不读 X"恰恰是本项目最容易犯的错：`ForceByLayer` 会覆盖 `LinetypeName`/`LineWeight`，
  `TargetGradientName` 优先于 `TargetPatternName`，`PatternDouble` 只在 `UserDefined` 下有意义。
  这些是**类型级**规则，属性元数据只能描述单字段，表达不了。

**修正：schema 归 `IRuleHandler` 所有。** 每个 handler 返回自己的字段清单（字段路径、中文标签、控件、
单位、候选值、生效默认值、可见性条件、必填），`RuleFactory` 已经是类型注册表，UI 直接向它要 schema。
自研规则类型实现自己的 schema，不碰共享模型，也不存在第二张表。类型级校验与类型级可见性规则跟着 handler 走，
`ConfigLoader.ValidateByType` 里那串 if-else 可以并进去，不再长出第四份。

### 二、"表单编辑不丢字段"在原方案下不可达

读取时 `MissingMemberHandling.Ignore` + 把 `JsonSerializationException` 标记为已处理
（`ConfigLoader.cs`），未知字段在**进内存时**就没了；写回时 `ConfigSaver.SaveRules` 用 `RuleJson.Serialize`
整段重写。表单编辑 = 反序列化 → 改 → 序列化，手写在 JSON 里的自定义字段必然被抹掉。
这是相对纯 JSON 编辑的**功能退步**，不是"风险"。

**修正：** `RuleFilter` / `RuleAction` 各加一个 `[JsonExtensionData] IDictionary<string, JToken> Extra`。
未知字段被接住并原样写回；表单不渲染它们，只在面板底部显示"另有 N 个未识别字段（已保留）"，JSON 预览里能看到。
顺带解决自研规则字段没有地方放的问题。

同时要认另一条：`SaveRules` 整段替换 `Rules` 数组，**数组内的注释会被删掉**。示例配置里
`config.json` 的字段级注释正是作者的说明书，表单保存一次就没了。这条原风险清单漏了，需要显式承认，
或者在保存前把注释块一并备份进 `.bak` 并在状态栏提示。

### 三、红/黄校验：现在没有 error 级别，也没有字段锚点

`ConfigLoader.ValidateByType` 只往 `List<string>` 里塞 warning，**没有任何 error 级别**；
且 11 种类型里只覆盖了 8 种，`PurgeUnused` / `EntityLineweightChange` / `SetByLayer` 零校验。
按原设计"红=阻断保存、沿用现有语义"是自相矛盾的。

**修正：** 一个校验器返回 `(字段路径, 级别, 文案)`，表单和 `ConfigLoader` 共用，红阻断保存、黄仅提醒。
未覆盖的 3 种类型补上校验，否则它们的红框永远不亮。列表行显示错误徽标，未选中规则的问题也看得见。

### 四、值域从图纸读：代价被低估，且解决的不是同一个问题

这是评审里分歧最大的一条（用户选了"从图纸读"，两个视角主张砍掉）。

- **图纸 ≠ 批处理目标。** 作者在 A 图上打开面板，候选里有 `A1_TITLE`，但配置要跑的是整个目录的图，
  目标图里没有这个块——问题原样复发，而且更隐蔽，因为下拉框看起来"有值"。
- **填充图案名不在符号表里**，来自 `acad.pat` / `acadiso.pat`；`PurgeCategories` 是固定枚举。
  "从当前图纸符号表读"覆盖不了这两类。
- **线程与锁没定义。** 非模式窗口在命令空闲期读符号表，不开文档锁可能 `eLockViolation`；
  事务谁开谁关、缓存何时失效、切图后如何刷新（全仓库没有 `DocumentActivated` 事件）都得新写。
- 上千个图层/块名时的下拉性能、`*U##` 匿名块过滤、候选为空 vs 读取失败 vs 无文档三态，都要各自定义行为。

**已决策（2026-10-29）：** 把"实时下拉"降级为"**保存时校验 + 最近匹配提示**"。
复用已有的 `LayerService` / `BlockNameUtil` / `TextStyleService` 对照符号表查一次，
不存在就报"图层 `A1_TITL` 不存在，最接近 `A1_TITLE`"，黄色提示不阻断。
零新接口、零 UI 依赖宿主、不受"当前打开的是哪张图"影响。
固定枚举（`Scope` / `PatternType` / `HatchStyle` / `PurgeCategories` / 颜色索引）仍做成下拉，
但值来自 schema 常量，不来自图纸。

### 五、拾取按钮：不是"同一套模式"，是一条新链路

`UiRunBridge` 是**单向**的（界面放请求 → 命令取一次即清空），`SendStringToExecute` 没有回传通道，
用户按 Esc 也没有通知。要做拾取，得再造一条带回调的桥 + 状态机（点了拾取 → 等待 → 回填 / 取消 / 超时），
并且所有失败路径都要写 `DiagnosticLog`，否则现场只有"点了没反应"。

**修正：** 保留，但只做块名与图层名两个字段，并明确三件事：Esc 视为取消并恢复按钮状态；
拾取期间窗口置底或最小化；每次拾取把命令回执状态写进诊断日志。

### 六、布局：分栏会压死列表，且吸顶分组没有现成控件

现窗口 `ClientSize` 735、`MinimumSize` 600，列表行按全宽渲染"过滤 → 操作"摘要。
分栏后右侧面板要 380+，列表摘要会被截断；把最小宽度抬到 860 以上，在 1366×768 的笔记本上不可用。
另外整个 UI 是手写 `Left/Top` 布局（`BuildEditPanel` 里全是魔数），`FlowLayoutPanel` 做不出吸顶分组，
需要自绘滚动容器。

**已决策（2026-10-29）：** 列表保持全宽不动；属性面板做成**双击规则行打开的模态抽屉**（约 900×600），
抽屉内固定三组「过滤 / 操作 / 高级」，空组隐藏。这样既不挤压列表，也不需要吸顶滚动容器。
窗口的 `ClientSize` 与 `MinimumSize` 保持现值。

### 七、"同事看得懂"目前靠摘要，而摘要有损

`RuleSummary.DescribeFilter` 不输出 `LayerNames`、`DimensionStyleName`、`TrueColor`、`Scope`、
`SkipLockedLayers`、`IncludeNestedBlocks`、`SourcePatternNames`；`DescribeAction` 对未知类型返回空串。
于是 `LayerNames=[A,B] → 图层 X` 会渲染成 `(全部) → 图层 X`——同事读到"改全图"，实际只改两层。
自研规则类型的摘要直接空白。

**修正：** 无论表单做不做，`RuleSummary` 都要补全：每个字段要么出现在摘要里，要么进"刻意不显示"白名单；
未显示的条件追加"+N 项条件"；未知类型回落到"类型 + 已设置字段数"。这一条独立于表单，可以先做。

### 八、其余必须写进设计的细节

| 问题 | 结论 |
|---|---|
| 三态布尔（`不设置 / 是 / 否`） | "不设置"读起来像"关闭"，但 `IncludeNestedBlocks`、`SkipLockedLayers`、`MigrateAttributes`、`CreateIfMissing`、`ForceColorByLayer` 的运行时默认都是 **true**。控件必须显示"不设置（默认：是）"，默认值由 schema 声明，不能抄第二份 |
| 切换 `Type` | 必须**清空新类型 schema 之外的字段**（有内容时先确认），否则残留字段不可见但继续生效——比 JSON 更危险 |
| 单/复数成对字段 | `LayerName`+`LayerNames`、`ColorIndex`+`ColorIndexes`、`SourceBlockName`+`SourceBlockNames`、`SourcePatternName`+`SourcePatternNames`：一个标签列表编辑器，1 项写单数、多项写复数 |
| "超过 8 个字段才分组" | 不可测且位置不稳定，改为固定三组、空组隐藏 |
| 规则级字段（`Name`/`Type`/`Enabled`/`ContinueOnError`） | 面板顶部固定区，不进三组 |
| JSON 只读预览 | 只读 + 「复制 JSON」；要手改就点已有的「打开配置文件」，不开第二条编辑通道 |
| 新增字段的成本 | 至少 6 处：模型属性、schema（现在归 handler）、类型级校验、`RuleSummary`、`Rules/*.cs`、过滤字段还要 `DxfFilter` |

## 目标与非目标

**目标**

- 作者改规则不需要记字段名和取值写法，且改完能立刻知道哪里不合法；
- 同事打开界面能看懂每条规则在做什么（摘要补全 + 字段中文标签 + 生效默认值可见）；
- 11 种内置类型 + 作者自研类型都被覆盖，自研类型的 schema 与校验自带；
- 表单编辑不丢字段（含手写与自研自定义字段）。

**非目标**

- 不做 `DryRun`（预演：只统计不落库）；
- 不新增规则类型（`LayerMerge`、文字查找替换只在讨论里出现）；
- 不做多人并发编辑、不做权限；
- 不做"从图上拾取"之外的交互式取值（框选一批对象反推条件等）；
- 不改变执行引擎、事务边界、日志格式。

## 已权衡并否决的替代方案

| 方案 | 否决理由 |
|---|---|
| 保留 JSON，只加字段骨架插入 + 自动补全 | 解决不了"不知道有哪些字段"，且要自建补全引擎，成本接近表单的一半 |
| WinForms `PropertyGrid` + `TypeConverter` | 中文标签与单位能硬塞，但视觉与现有自绘风格不搭，也无法按类型裁剪字段 |
| 每种规则手写一个 `Form` | 11 种 × 平均 10 字段，改一个字段要动多处，自研规则还得再写一个 |
| JSON Schema 文件 + 生成表单 | 要与模型双向保持一致，收益同属性标注、成本更高 |
| **属性标注 + 按类型注册表（原设计）** | 两份账、断言恒真、表达不了类型级可见性与互斥，见"分析一" |
| 表单与 JSON 双向实时同步 | 冲突合并、报错定位、光标状态成本极高；JSON 只读后问题消失 |
| **实时下拉 vs 保存时校验（值域）** | 实时下拉受"当前打开哪张图"影响，且覆盖不了 .pat 图案名；保存时校验更便宜、更准，见"分析四" |
| **右侧常驻面板 vs 模态抽屉（布局）** | 735 宽下常驻面板会压死列表摘要，见"分析六" |

## 关键决策（定稿）

> **2026-10-29 修订：决策 1 被推翻。** 起草阶段用户选择"属性反射推导"（在 `RuleFilter`/`RuleAction`
> 属性上标注 `[RuleField]`），schema 不再归 `IRuleHandler`。连带作废"分析一"中"属性标注方案不可用"的结论。
> 为此接受两项代价并在设计中显式处理：类型级联动改用 `VisibleWhen` 条件表达式；
> `AppliesTo` 与 handler 实际读取逻辑仍是两份账，靠启动断言 + 每类型最小配置回归测试兜。
> 其余决策不变。

1. ~~**schema 归 `IRuleHandler`**~~ → **改为：属性标注是唯一事实源。**
   在 `RuleFilter` / `RuleAction` 的属性上标 `[RuleField(Label, Editor, AppliesTo, Group, Order, Unit,
   Values, Default, VisibleWhen, Required, ValidateAs, Help)]`；UI 反射这些属性生成控件，
   按 `AppliesTo` 过滤当前类型可见的字段。新增字段 = 加一个属性 + 标一次注。
   `RuleFactory` 仍是类型清单的唯一注册入口（类型下拉从它取）。
2. **JSON 只读预览**，不提供第二编辑通道；手改走「打开配置文件」。
3. **`Extra` 扩展字段袋**（`[JsonExtensionData]`）保证未知字段往返不丢；表单底部提示"N 个未识别字段已保留"。
4. **单一校验器**返回 `(字段路径, 级别, 文案)`，红阻断 / 黄提醒，补齐 3 种零校验的类型。
5. **切换类型清空非本类型字段**，有内容时二次确认。
6. **布局**：列表保持全宽，属性面板为**模态抽屉**（900×600），固定三组、空组隐藏；
   窗口尺寸不变。
7. **值域**：固定枚举来自 schema 常量；图纸相关名称（图层/块/文字样式/标注样式/线型）走
   **保存时校验 + 最近匹配提示**（黄色不阻断），不做实时下拉。
   ~~不引入 `IRuleValueProvider`~~ → **2026-10-29 修订：允许且仅允许新增一个名称查询接口**
   （`INameLookup` + 宿主实现 `HostNameLookup`，宿主类型只出现在实现类里）。
   理由是保存时校验必须读符号表，而 `LayerService`/`BlockNameUtil` 的签名直接吃 `Transaction`/`Database`，
   让 UI 调它们就破坏了"UI 不引用宿主类型"。除此之外不新增任何接口。
   填充图案名不在符号表，只校验非空，不尝试解析 .pat。
8. **拾取**：只做块名与图层名；新桥带回调；Esc=取消；全程写 `DiagnosticLog`。
9. **`RuleSummary` 补全**独立先做，覆盖全部字段与未知类型。
10. **无图纸**只提示不降级（`BATCHUI` 本身要求有活动文档，该路径很少走到）。

## 建议的实施顺序

> **2026-10-29 评审后修订**：`egm-review` 判定 13 条阻断项里 8 条由表单机制自身产生。
> 经用户裁决，**P2（表单）与 P3（拾取）推迟到下一轮**，本轮只交付 P0 + P1。
> 详细设计见 `docs/designs/rule-editor-form.md`；遗留项清单见该文末"下一轮遗留项"。
> 同时新增一条约束：`Filter` 字段分"引擎级（`DxfFilter` 无条件读取，永不可隐藏）"与
> "handler 级（按类型显示）"两类，`AppliesTo="*"` 不足以表达前者。

| 阶段 | 内容 | 为什么这个顺序 |
|---|---|---|
| P0 | `RuleSummary` 补全 + 保存时名称校验（最近匹配）+ 修 `IncludeNestedBlocks` 死字段 | 不依赖 schema，独立可交付，直接消灭"打错一个字 0 命中"与"同事误读摘要" |
| P1 | `Extra` 字段袋 + 单一校验器 | 是 P2 的前置；先保证往返不丢字段，否则表单会静默毁配置 |
| P2（下一轮） | `[RuleField]` 标注 + 抽屉表单 | 需先清掉"下一轮遗留项"表里的 11 条 |
| P3（下一轮） | 拾取（块名/图层名） | 最贵、最独立，做不完不影响主路径 |

## 评审中保留的未决细节（不阻断开工）

- 每类型字段清单的具体内容（11 类型 × 字段路径 × 标签 × 控件 × 单位）需要在 P2 里逐条写出来，
  这份数据量比代码量大，是本阶段最容易被低估的部分。
- 保存时"最近匹配"用编辑距离还是前缀匹配、阈值多少，实现时定。
- `RuleDetailForm`（现有双击查看详情窗口）与新的只读 JSON 预览是否合并，实现时定。
